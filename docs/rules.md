# 列车识别规则管理

## 网页操作

打开侧栏“规则管理”。没有知识库时，可点击“创建铁路知识库”。
有多个知识库时，先选择知识库，再点击“新建规则”。
列表可按名称、条件、结论搜索，并筛选启用或停用状态。
点击“编辑”可修改整条规则，包括启停状态；保存后写入 SQLite。
展开列表行可查看来源链接和备注。删除前有确认对话框。

## 规则结构

一条规则包含名称、前提条件、条件关系、推导结论、优先级、启用状态、来源和备注。
前提条件为“字段、运算符、值”，支持 1–30 个条件。
条件关系支持全部满足（AND）或任一满足（OR）。
结论可以是候选车型，也可以是供后续规则使用的中间特征。
优先级为 0–999 的整数，数值越大越优先。当前列表按优先级、编号降序排列。

可用字段包含系列、品牌、车型状态、设计速度、运营速度、最高实验速度、车辆数量、动力编组、
动力形式、用途、外观特征、适用环境、已推导特征。
速度单位统一为 km/h，三个速度字段独立保存，不能混用。
数字条件支持等于、不等于、大于、大于等于、小于、小于等于；文本支持等于、
不等于、包含。数值范围为 0–1000，车辆数量必须是正整数。
“不等于”是显式比较条件，未来推理时不能把未知值当作不等于。

规则应基于车型详情资料，并在备注中写明适用批次。
仅凭相同速度和编组不能保证唯一确定车型，结论应由足够的特征支持。
已按来源导入 CR、CRH 车型候选规则。资料不足的记录保持停用。
完整范围、参数口径和差异见 [导入记录](railway-import-2026-10-22.md)。

规则可在推理工作台执行，算法与候选核验方式见 [推理文档](inference.md)。
事实管理已支持结构化条目的增删改查，使用方式见 [事实管理文档](facts.md)。
已实现文件导出和推理记录；[Neo4j 知识图谱](knowledge-graph.md) 已完成建模、页面和本机数据库联调。

## 数据接口

所有规则归属知识库，其他知识库路径不能访问或修改这些规则。

```text
GET    /api/knowledge-bases/:baseId/rules
POST   /api/knowledge-bases/:baseId/rules
GET    /api/knowledge-bases/:baseId/rules/:ruleId
PUT    /api/knowledge-bases/:baseId/rules/:ruleId
DELETE /api/knowledge-bases/:baseId/rules/:ruleId
```

POST 和 PUT 使用相同的完整数据结构。PUT 不用于跨知识库移动规则。

```json
{
  "name": "规则名称",
  "conditions": [
    { "field": "design_speed", "operator": "eq", "value": 350 }
  ],
  "conclusion": "待核对的候选车型或中间特征",
  "match_mode": "all",
  "priority": 0,
  "enabled": true,
  "source_url": "",
  "notes": "结构示例，不是已验证的车型识别规则"
}
```

服务端校验字段、运算符、值类型、长度、优先级和来源 URL。
错误数据返回 400，不存在或不属于当前知识库的规则返回 404。
旧版数据库启动时会自动事务升级至版本 5，保留已有数据。
导入键和来源快照独立保存；网页编辑不会清除导入键，再次导入不会覆盖手工编辑。
